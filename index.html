Docs-as-Code at scale

One versioned source for documentation that many client banks receive, with the website, PDF and in-app help built from it.

Role: initiative owner, architecture, DocOps on the pilot · Stack: Markdown, Zensical, Sphinx, GitLab CI

See the live demo site →

The problem

Documentation was kept in Word, PDF and a wiki, and many documents were customised copies for one client. Every product change had to be carried into each copy by hand, and the copies drifted apart.

What was built

  • One source in Git: shared text written once, client differences in separate layers.
  • A bilingual help site and a PDF built from it in CI, with link, style and screenshot checks.
  • The “?” button in the application opens the matching help section.

Key decisions

Three tools compared on real documentation

Problem
The shortlist had never been tested on production content.
Choice
The same fragments built in Zensical, Antora and Sphinx; 19 features checked in HTML and PDF.

Layers, not branches

Problem
Client variants must follow the shared text without copying.
Choice
Layer folders on top of a common base, with a working prototype.

A DocOps role

Problem
Without an owner, a pipeline decays.
Choice
A defined role with duties, boundaries and success criteria.

Where it broke

In some tools, client variants built as conditional text still appeared in another client’s navigation and search. Now every tool is checked for this on real fragments before it is chosen.

Result

A working pilot: bilingual help site, PDF and in-app help from one source. 19 features compared across three tools on real documentation.
