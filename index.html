Docs-as-Code at scale

Moving a large, multi-client documentation base from Word and wikis to one versioned source — with automated builds, checks and help opened right from the application.

I lead the transition: approach, architecture, migration plan and its defence. On the pilot I also did the engineering part myself — tooling, builds, checks and release. This page explains the problem, the decisions and where the project stands.

2026 Enterprise financial software Role: initiative owner, architecture, DocOps on the pilot Markdown · Zensical · GitLab CI · Pandoc

The problem

Thousands of documents across more than a hundred modules, kept in Word, PDF and a wiki, delivered to many client organisations. A large share of them are customised copies for a particular client.

One product change has to be carried by hand into every copy — and the copies drift apart. Every new client adds more manual work.

What was built

One source

Documentation in Markdown under Git. Shared content is written once; client differences live in separate layers.

Automated build

A branded help site in two languages, with search and offline use, and a PDF from the same source — built in CI.

Help in context

The “?” button in the application opens the matching section of the help.

Plus team tooling: link, style and screenshot checks before changes reach the main branch, a PDF generator, a project template for a new client and guides for writers. Public versions: docs-toolkit, zensical-to-pdf, live demo: IB Docs — Zensical.

The core idea: shared content and client layers

Instead of a full copy per client, the documentation is assembled from a common base and a thin client layer. One change in the base reaches every client at the next build.

Key decisions

A mini-pilot before choosing the tool

Problem
The scale of the core system cannot be tested on a pilot for one client.
Choice
First a mini-pilot on 5–7 real documents, and the tool is chosen from its results — not the full migration at once.

Three stacks compared on real documentation

Problem
The shortlist had two candidates and had never been checked against production content.
Options
Markdown + Zensical, AsciiDoc + Antora, and a third one I added: Sphinx + MyST.
Choice
The same fragments built in each stack, 19 features checked in HTML and PDF — conditional text per client, includes, variables, numbering, cross-references, complex tables, modules as separate sites with shared search. The pilot site (~50 pages, two languages) was migrated to Sphinx and built side by side. Non-obvious limits found, such as another client’s text leaking into navigation and search. Result: a comparison table by build and delivery, authoring and operations, and a recommendation.

Layers instead of branches for client differences

Problem
Client variants must stay in sync with the base without manual copying.
Options
A Git branch per client, or layer folders on top of a common base.
Choice
Worked out together with a technical specialist; a working prototype of layered builds with a context-help map for three test clients.

Migration in phases, measured after each

Problem
The transition runs alongside the team’s everyday work.
Choice
An inventory by module and client, a rough effort estimate, then phased migration with a measurement after every phase, a reserved share of team time and training on pilot material. Delivery of the built help to client servers agreed with DevOps.

A DocOps role, not “the writers will manage”

Problem
A pipeline needs an owner; without one it decays or moves to developers.
Choice
A role profile: one-off and ongoing duties, boundaries with DevOps and development, skills, success criteria and a workload review based on measurements.

Where it stands

  • Working pilot: branded bilingual help opened from the application, PDF from the same source. MVP defended before leadership.
  • The approach is accepted as shared; other products are ready to join.
  • Architecture and phased plan presented to leadership.

Honestly about the status. This is a defended pilot and a plan, not a completed migration. Effort figures stay estimates until the mini-pilot measures them.

What is not solved yet

  • Final tool choice — after the mini-pilot.
  • Migration of the core system — phased, not started at scale.
  • Effect not measured yet: time per update, documents touched per change.
